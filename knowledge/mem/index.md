# Project Memory

## Core
This is a Kajabi theme exporter and dynamic renderer. **Authoring surface = the React block components we've built first-class editors for (~16 atomic blocks + 3 section types: Header/Content/Footer).** **Rendering + export surface = whatever the imported base-theme zip declares** (registry-driven via `packages/engine/src/engines/schemaRegistry.ts`, generated from each theme's `{% schema %}`). Unknown blocks round-trip as opaque (`__opaque:true`) so they survive byte-identically. Never hand-author opaque blocks; do prefer canonical first-class blocks when they exist.
Page shape: exactly 1 `<HeaderSection>` + 1–8 `<ContentSection>` + 1 `<FooterSection>`. The footer slot serializes as `footer` on Standard themes and `footer_pro` on Pro themes — same `<FooterSection>` component, exporter picks the right output type.
Header allowlist (verified, all 4 themes): `logo`, `menu`, `dropdown`, `user`, `cta`, `hello_bar`, `social_icons`. Footer (Standard): `logo`, `link_list`, `copyright`, `social_icons`. Footer Pro (`footer_pro`, Pro themes only) ALSO accepts: `accordion`, `audio`, `assessment`, `blog`, `cta`, `countdown`, `code`, `card`, `event`, `event_video`, `feature`, `form`, `image`, `multi_video`, `offer`, `pricing`, `text`, `video`, `video_embed`, `external_widget`. Putting Pro-footer blocks on a Standard site = silent drop. For wordmarks always use `logo` block (`logoType:"text"`), never `text`. See AGENTS §4.27 + `mem://reference/header-footer-block-allowlist.md`.
🚨 NEVER INVENT SCHEMA FIELD IDS — for EVERY themeSettings/section/block field you write, verify the exact field ID exists in the base theme's parsed schema BEFORE saving. Sources: `packages/engine/src/engines/schemaRegistry.ts` / `schemas.generated.json`, `mem://reference/pro-custom-fonts.md` (+ value-formats), `mem://reference/block-field-catalog.md`, or extract `config/settings_schema.json` from the base theme zip directly. Made-up names (e.g. `primary_font_link`, `accent_font_family`) sit valid in JSON, save returns 200 OK, but the Style Guide UI stays blank because the real fields were never written. Same class of silent-drop bug as §4.26 block prop names. Pre-flight: list every field ID, grep the schema for each, fix any that don't exist. See `mem://reference/never-invent-schema-field-ids.md`.
🚨 PRO ≠ STANDARD STYLE-GUIDE FIELD IDS — Pro themes (`-pro`) use DIFFERENT field IDs than Standard for the same Style Guide controls. Standard `color_button`/`color_button_text`/`color_background`/`color_text` DO NOT EXIST in the Pro template schema; Pro uses `btn_background_color`/`btn_text_color`/`background_color`/`color_body` (+ `color_heading`). Writing only Standard names on a Pro site → live site looks right via inheritance, but the Pro Style Guide UI shows the engine's brand-orange fallback `#ff3e14` because the Pro field was never written. Verified Carrie Variation 2026-05-10. Always grep `schemas.generated.json` under `themes['<base_theme>'].templateSettings` before writing themeSettings color/button/bg fields; write BOTH the Pro field AND the Standard sibling. Companion to §4.35ad: when Pro `use_custom_fonts` configures fonts, NEVER duplicate the same fonts in `customCss` `@import`+`body{font-family}` — silently overrides Style Guide edits. AGENTS §4.35am + `mem://reference/pro-vs-standard-field-ids.md`.
🚨 TEXT BLOCK CONTENT FIELD IS `text`, NEVER `html`/`content`/`body`/`richText` — most common §4.26 silent-drop. `<Text>` reads `props.text` only. AI repeatedly invents `props.html` because it "feels natural"; renderer draws nothing, save returns 200, expert sees blank sections everywhere (verified Verdant Carrie variation 2026-05-11, 38 blocks across one site). Engine 0.7.85+ forgives via aliasTextProps + serializer fallback for `html`/`content`/`body`/`richText`/`rich_text`, but AUTHOR THE CANONICAL `text` FIELD. Pre-flight every text-block save: grep `"html":`/`"content":`/`"body":` inside `type:"text"` blocks; rename to `text`. Same trap on `feature` (use `text` not `description`), `cta` (use `label`), `pricing_card` (use `name`+`text`+`heading`). See `mem://reference/text-block-content-field-is-text-not-html.md`.
🚨 SHARED HEADER + FOOTER MUST BE BRANDED BEFORE DECLARING A SITE DONE — #1 missed step on new builds. `createSite` auto-seeds `sharedHeader`/`sharedFooter`/`sharedFooterPro` with the base theme's defaults ("Encore"/"Streamlined" wordmark, placeholder nav, default link columns). If the AI walks page-by-page composing content sections and never touches the shared chrome, expert immediately reports "the header still says Encore." Header MUST have real `logo` block (NEVER `text` — silently dropped), real `menu` with actual page links, branded `background`. Footer MUST have brand wordmark/logo, real `link_list` columns (NOT placeholder "Quick Links/Support/Legal"), branded `copyright` (no leading ©/year), branded `background`. Pro: also `merge_powered_by_with_copyright:"true"` + hide Standard footer. Pre-flight EVERY new site BEFORE declaring done: walk `design.sharedHeader` + `sharedFooter` (+ `sharedFooterPro` on Pro); is every brand asset/name real, not base-theme placeholder? Are menu/link_list entries real? Verified Verdant Carrie variation 2026-05-11. AGENTS §4.35an + `mem://reference/shared-header-footer-must-be-branded.md`.
🚨 GENERATED PERSON/FIGURE IMAGES MUST BE VISUALLY INSPECTED BEFORE WIRING — image-gen models fail ~1 in 4 on figures (extra fingers, fused limbs, twisted torsos, distorted hands). Treating gen as fire-and-forget guarantees ~25% of person images on a finished site are broken. Verified Verdant Carrie variation 2026-05-11: 3 of 12 person images had defects (deformed chest/arms hero, warped hands offer1, distorted posture lifestyle1), none caught during build. Inspect every figure image via `code--view` (renders inline) BEFORE upload+wire; check hands (count fingers), limbs (symmetry+joints), torso, faces, posture. Regenerate or reframe (crop hands out, profile angle) any defects. Does NOT apply to landscapes/products/textures/food/plants. Letting the expert be first human eyes = process bug, not content bug. AGENTS §4.35ao + `mem://reference/person-image-anatomy-qa.md`.
Read `src/engines/kajabi_rendering_guide.md` and `mem://reference/section-layout-gotchas.md` BEFORE writing block/section code.
Export pipeline supports single page OR multi-page: `exportFromTree(tree)` for homepage only, or `exportFromTree({ index, about, contact, ... })` for multi-page. Then `triggerDownload(blob, 'site.zip')`. Never write a custom serializer.
Multi-page: header/footer are SHARED site-wide — extract `<SharedHeader/>`/`<SharedFooter/>` and include in every page tree. Last definition wins.
Adding pages: NEVER use `(page)` or `(sales_page)` templates. For each new page create `templates/<name>.liquid` containing `{% dynamic_sections_for "<name>" %}`, define section instances in `settings_data.json` under `current.sections`, and register `content_for_<name>: [section_ids_in_order]` at the bottom. Template filename, tag arg, and JSON key MUST match. See `mem://reference/kajabi-page-creation.md`.
Deleting pages: NEVER delete Kajabi system pages (Home, Announcements, Newsletter Subscribe, 404, Thank You, Newsletter, Newsletter Post, Login, Blog Post, Blog, Store, Library, Blog Search, Member Directory). Only non-system pages (e.g. About, Contact) and custom-added pages may be removed. To delete: remove `templates/<name>.liquid`, drop its sections from `current.sections`, and delete its `content_for_<name>` array.
DYNAMIC PAGES (CRITICAL — AUDIT EVERY SITE) — NEVER hardcode posts/products/lessons on `blog`, `blog_post`, `library`, `store`, `login`, `register`, `forgot_password`, `reset_password`, `thank_you`, `404`, `newsletter*`, `member_directory`, `announcements`, `blog_search`. Kajabi renders these from the expert's real data at runtime — hardcoded mock cards/posts/products HIDE the real content. Required raw sections: `library` → `{ kind: "raw", type: "products" }` (or `<RawSection type="products">` in JSX), `blog` → `{ kind: "raw", type: "blog_listings" }`, `blog_post` → `{ kind: "raw", type: "blog_post_body" }`. Always pass branded `settings` (background_color, text_color, btn_background_color, btn_text_color, btn_border_radius, btn_style — match other CTAs on the site). Allowed page shape: header + optional branded intro `content` section (eyebrow + h1 + lede only, NO fake cards) + raw section + optional outro CTA + footer. Pre-flight before saving any of these pages: scan for `card`/`feature`/`text` blocks containing mock posts/products/lessons and replace with the raw section. See `mem://workflow/template-dynamic-content-audit.md` and AGENTS §4.10.
PAGE TEMPLATE IS OFF-LIMITS — `design.pages.page` MUST be header + footer only (sections.length === 2). The `page` template is Kajabi's per-product wrapper, reused for every course/sales/landing page the expert publishes; anything composed into it gets injected on top of every product. If the expert says "design the page", they mean a specific named page — confirm which and edit that page key, never `page`. See AGENTS §4.11.
AUTH PAGES OFF-LIMITS — `design.pages.login`, `register`, `forgot_password`, `reset_password` MUST be header + footer only (sections.length === 2). They are non-composable in Kajabi: `login.liquid` uses built-in `{% section "login" %}`, `forgot_password.liquid` hardcodes `{% include "block_password_reset" %}`, `forgot_password_edit.liquid` (= reset_password) hardcodes `{% include "block_password_edit" %}`, `register` doesn't exist as a template. Any composed content is either ignored or renders ON TOP of Kajabi's real form. NEVER add fake login forms, "welcome back" headlines, signup CTAs, or branded intros to these pages — branding flows through `themeSettings` only. See AGENTS §4.10.
TEMPLATE-WIDE BRANDING — every template should set `themeSettings` (typed fields from `templateSettingsCatalog.ts`) and `customCss` on its `TemplateDef` so Kajabi system pages (login/store/checkout) inherit the brand. See `mem://feature/template-theme-settings.md`.
FOOTER COPYRIGHT — `copyright` block text MUST start directly with the brand/owner name. NEVER include leading `©`, `Copyright`, or any 4-digit year — Kajabi auto-prepends `© <current year> ` to the text. Writing `"© 2026 Acme"` ships as `"© 2026 © 2026 Acme"`. Pre-flight every footer: strip leading `©`/`Copyright`/year from every `copyright` block. See AGENTS §4.13.
SocialIcons render only when each platform URL is set. 🚨 `social_icons` ALSO needs explicit `iconColor` (+ snake_case `icon_color` + `color`) when section bg differs from body palette — defaults to body text color and goes invisible on inverted footers (dark footer + dark icons = blend). Verified Verdant 2026-05-11. Add to §4.35al-style button-contrast audit. See `mem://reference/social-icons-contrast.md`.
`background_color` over `bg_image`/`bg_video` must be `rgba(...)` with a<1, OR empty string `""` to show the raw image — opaque hex/rgb/rgba(a=1) covers the image entirely. Same rule for section `background` prop when `bgType: 'image'`. Default to `""` unless an explicit tint is requested.
`fullWidth` is inner-content breakout, NOT image coverage. `horizontal` (section) is block alignment in 12-col grid, not text alignment. `vertical: center` only works with `fullHeight: true`.
SECTION FULL WIDTH — NEVER set `fullWidth: true` on a `ContentSection` unless the expert explicitly asked for "full width / edge to edge / full bleed". Default is constrained (1170px). "Make it bigger / more premium / more impactful" does NOT mean full width — that means more padding, bigger type, or stronger background. Background images already cover the full viewport via `bg_image` + `background-size: cover`; `fullWidth` only stretches the inner text/blocks and makes headlines run 2000px+ wide. Pre-flight every template/page: scan content sections, strip any unrequested `fullWidth: true`. See AGENTS §4.12.
SECTION maxWidth IS RENDERER-ONLY (silent-drop on export) — NEVER set `maxWidth` (or any width-clamp CSS) on a `ContentSection`. Kajabi's section schema has no `max_width` field; the serializer drops it. Preview shows tidy ~3/4-width centered column, live Kajabi renders full-bleed because inner blocks are still `width: "12"`. Constrain layout via the 12-COLUMN BLOCK GRID instead — set EVERY block in the section (including the heading text block) to `width: "8"` (standard centered) / `"6"` (tight reading column) / `"10"` (loose) + `align: "center"`. The grid is the only width primitive that survives export; both preview and Kajabi honor it identically. Symptom: "centered narrow in preview, full-bleed on Kajabi". Companion to SECTION FULL WIDTH (the inverse mistake). See AGENTS §4.28 + `mem://reference/section-maxwidth-silent-drop.md`.

TEMPLATE TYPOGRAPHY DIVERSITY (CRITICAL) — every new template MUST use a font pairing not already registered in `src/templates/*.tsx`. Run `grep -hE "fonts: \{" src/templates/*.tsx` BEFORE picking fonts. SECTION NAMING — every `<ContentSection>` MUST pass a `name` prop (e.g. "Hero", "Community", "FAQ") so Kajabi's editor sidebar shows meaningful labels instead of "Section / Section / Section". See `mem://feature/section-naming.md`.
TEMPLATE/PAGE NAMES: input regex allows hyphens (`/^[a-z0-9_-]{1,48}$/` in `serialize.ts` + `exportEngine.ts`) BUT the emitted Kajabi handle MUST be snake_case — `dynamic_sections_for "<handle>"` rejects hyphens/spaces/uppercase. Engine auto-sanitizes via `sanitizeTemplateHandle()` (replaces `-`→`_`) when emitting `content_for_<handle>`, the `templates/<handle>.liquid` filename, and the `dynamic_sections_for` arg. Author new page keys directly in snake_case (`level_1_foundation`, not `level-1-foundation`) — hyphenated keys still work via auto-sanitize but are noisy. Symptom of pre-sanitizer engines: Kajabi rejects upload as Invalid Template / custom pages 404. See `mem://reference/template-name-handle-snake-case.md` and `mem://reference/template-name-validation.md`.
NEVER set a block's `background_color` (or any color field) to the string `"transparent"` — Kajabi treats it as a literal CSS value and breaks downstream styling. Leave the value as `""` (empty string) when you want no background. Same rule for `text_color`, `btn_background_color`, `btn_text_color`, etc. — empty string, never `"transparent"`.
SECTION BACKGROUND IMAGES go directly into `bg_image` JSON (same as block images) — Kajabi's `image_picker_url` filter passes external `https://` URLs through unchanged. The old CSS-injection workaround (`__externalBg`, `buildExternalBgCssBlock`, `assets/inject.css`) is REMOVED. If you reintroduce it you'll silently break exports for thin clients on synced engines. See serialize.ts `if (layout.backgroundImage) settings.bg_image = layout.backgroundImage;`.
ASSET BUNDLING (default ON for site AND landing_page; bundle is PRIMARY, no Supabase fallback) — Export pipeline (`packages/engine/src/engines/bundleAssets.ts`, called from `exportThemeZip`) downloads every external `bg_image`/`image` URL in `settings_data.json`, writes bytes to `assets/<hash>.<ext>`, emits `snippets/bundled_assets.liquid` mapping section/block IDs → filenames, and patches `snippets/{section_styles,block_image,block_feature}.liquid` so the bundle resolver is consulted FIRST (placeholder is the only fallback). After bundling, the JSON `bg_image`/`image` field is **stripped to `""`** — the exported zip is fully self-contained and has zero runtime dependency on Supabase or any external CDN. Supabase remains source-of-truth at EXPORT time only (engine `fetch()`es bytes fresh on every re-export); shipped Kajabi sites never call back. Opt out with `exportThemeZip(..., { bundleAssets: false })` for debugging only. See `mem://feature/asset-bundling-export.md`.
CTA BUTTONS — every CTA on a single site MUST look identical and on-brand (same `buttonBackgroundColor`, `buttonTextColor`, `buttonStyle`, `buttonBorderRadius`). Per-block styling is FINE and often necessary; the bug is INCONSISTENCY across CTAs (one navy pill, one cream square). Before editing one CTA, audit every other `cta` block on the site and match. Pull colors from `themeSettings` (`color_button`, `color_button_text`, `color_primary`) when present. Reserve outline/ghost variants only for true secondary actions next to a primary CTA in the same section.
BLOCK CHROME KEY HYGIENE (CRITICAL silent-drop trap) — Chrome props on EVERY block MUST be camelCase, `padding` MUST be a 4-sided object. TWO failure modes both sit valid in JSON and produce ZERO visual effect: (1) scalar padding `"32"` or `32` → `JSON.parse` returns number not object → undefined → no rules emitted (ALWAYS use `padding: { top: "32", right: "32", bottom: "32", left: "32" }` even for uniform); (2) snake_case keys (`border_radius`, `background_color`, `box_shadow`, `image_width`, `btn_background_color`) silently ignored — serializer only reads camelCase (`borderRadius`, `backgroundColor`, `boxShadow`, `imageWidth`, `buttonBackgroundColor`). Confusion source: Kajabi `settings_data.json` exports use snake_case; engine React props use camelCase; serializer translates at export. Author camelCase in `design` JSON; snake_case is output-only. Border radius value has NO `px` suffix (`"16"` correct, `"16px"` becomes `16pxpx`). Symptom → diagnosis: "padding set but text flush to edge"=scalar padding; "still square corners"=border_radius vs borderRadius; "background color not showing"=background_color vs backgroundColor; "shadow not applying"=box_shadow vs boxShadow; "feature image still tiny despite image_width 480"=image_width vs imageWidth (also §4.17). Pre-flight every block: scan for underscore in chrome-prop keys → rename camelCase + delete snake_case; confirm padding is 4-sided object; confirm borderRadius has no `px`. For `feature` blocks rendering a button, the button is a SIBLING of the text HTML inside chrome — wrapping copy in `<div style="padding:28px">` does NOT pad the button. Either set chrome `padding` (object form) OR inline the button as an `<a>` inside the same wrapper div with `showButton: false`. See AGENTS §4.25 + `mem://reference/block-chrome-key-hygiene.md` + `mem://reference/block-padding-must-be-object.md`.
PRO THEMES — `sites.base_theme` can be `streamlined-home`, `streamlined-home-pro`, `encore-page`, or `encore-page-pro` (NULL = legacy → Standard via `resolveBaseTheme(site)`). Pro themes are ADDITIVE: every Standard block/field works identically. Pro adds extra blocks (`block_feature_icon`, `block_code_tabs`, `block_search_filter`), column slider variants, `footer_pro`, ~50 extra section-level fields, dark/light button+form pair model with `"inherit"` override sentinel (literal string, every override field), any-`<link>` custom fonts (Google/Adobe/self-hosted) with primary+accent slots, and `custom_css_class` on every section. Also see AGENTS §8.8.
PRO STYLING — typography, button, and form rules belong in `themeSettings` (sitewide) or block-level overrides (per-CTA), NEVER inline `style="..."` in block HTML. Inline CSS bypasses the global style guide, can't be edited from Kajabi's UI, and silently breaks when the expert tweaks a setting. Before adding any inline font/button/form CSS, audit existing inline rules and lift recurring ones into `themeSettings`. Every override field is enum-validated — emit `"Npx"` strings (px grid), unitless decimals on the 0.1 grid for line-height, 5px-grid for margins, `[-2px,2px]` for letter-spacing (NEVER `em`), and `"inherit"` (literal string) for fields you don't want to change (NEVER `""` or omit). Whenever you emit any override, flip its `hide_if` visibility toggle to `"true"`. Mind hyphen-in-ID fields: `*_line-height`, `*_letter-spacing`, `custom_body_button_line-height`. Full workflow + checklist + worked example: AGENTS §9.8e. Value enums: `mem://reference/pro-custom-fonts-value-formats.md`. Field reference: `mem://reference/pro-custom-fonts.md`.
NATIVE BLOCK BUTTONS — for any "Explore →" / "Learn more" / "Read story" CTA at the bottom of a `feature` or `pricing_card`, use the block's native button props (`showButton: true`, `buttonText`, `buttonUrl`, `buttonStyle: "text"` for low-emphasis or `"solid"`/`"outline"`, `buttonTextColor`, `buttonSize`) — NEVER bake an `<a>` into the HTML `text`. Inline `<a>`s bypass Kajabi's global button system, are invisible to §4.7's CTA consistency audit, and lose all per-block `btn_*` overrides. `feature` accepts `buttonStyle: "text"` (Pro renders full `block_cta` text-link styling). For `text` blocks (no native button), use a SIBLING `cta` block, not inline `<a>`. Allowed inline `<a>`: word-inside-a-sentence links, multiple links in one paragraph. Pre-flight: scan every feature/pricing_card text HTML for trailing `<p>...<a>...</a></p>` and lift them. Full reference: AGENTS §4.15 + `mem://reference/native-block-buttons-over-inline.md`.
TEXT BUTTON COLOR QUIRK (verified in Pro `block_cta.liquid` lines 181–211) — when `buttonStyle: "text"`, the visible link color comes from the dark/light pair slot matching `btn_type`, NOT from "buttonTextColor". `btn_type: "dark"` (default) → color = `buttonBackgroundColor`. `btn_type: "light"` → color = `buttonTextColor`. Mnemonic: "the color matches btn_type." Setting `buttonTextColor` on a default text button is a silent no-op — link renders in body color. For default (dark) text buttons put the accent on `buttonBackgroundColor`. Solid/outline buttons unaffected. Pre-flight: any text button with `buttonTextColor` set but `buttonBackgroundColor` empty is broken — swap them. Full reference: AGENTS §4.16 + `mem://reference/text-button-color-quirk.md`.
FONT CONTROLS BEFORE CSS — Use Kajabi's font pickers (`themeSettings.font_family_*` Standard, or Pro custom fonts via `use_custom_fonts:"true"` + `override_*_font_styles`) FIRST. NEVER hand-write `:root{--pathx-font-*}` or `body h1{font-family:...}` into `customCss`. The legacy `TreeGlobal.headingFont/bodyFont` injection in `export.ts` (`buildFontCssBlock` → `--pathx-font-heading/body`) emits a `body h1, body h2, ...` selector with higher specificity than Pro's `:is(h1,...)` overrides — if both run, legacy wins and silently replaces the expert's Pro font with whatever `resolveFont(headingFont)` defaults to (Inter when undefined). Symptom: "heading font is different in preview vs Kajabi." Fix lives in `exportFromTree`: `themeSettingsConfigureFonts(opts.themeSettings)` clears `headingFont/bodyFont/fontImports` from `opts.global` whenever themeSettings drives fonts. See `mem://feature/font-controls-before-css.md`.

SLIDER `block_offset` IS MANDATORY (Pro #1 mistake) — Pro slider pulls EVERY block in the section into the slide pool by default, INCLUDING intro eyebrow/headline/lede. Symptom: "the headline is sliding past as a slide" / "you forgot to skip one block before starting the slider" / "my title is in the carousel". PRICING CARD STRUCTURE — `PricingCard.tsx` mirrors Kajabi `block_pricing.liquid` 1:1: `<div class="pricing"><div class="pricing__body">name(h4) → price(h2) → heading(p caption) → text(.pricing__content) → CTA → secondary CTA</div></div>`. Use Kajabi class names (`pricing__name/info/price/heading/content`, `custom-icon`) so themeSettings sitewide CSS reaches the preview. `heading` is the canonical caption field (e.g. "paid in full"); `priceCaption` kept as back-compat alias. Outline button branch must use `backgroundColor:'transparent'`. See `mem://reference/pricing-card-kajabi-structure.md` and AGENTS §4.19.
PRO ALL-HEADINGS FONT — to apply a custom Pro font to ALL headings sitewide (the DEFAULT and SAFE choice), set `override_heading_font_styles:"true"` + `select_custom_all_headings_font:"primary"` (or `"accent"`). 🚨 Naming asymmetry trap: the toggle is singular (`_heading_`) but every child field is plural (`_all_headings_`): `select_custom_all_headings_font`, `custom_all_headings_font_weight`, `custom_all_headings_line-height`, `custom_all_headings_letter-spacing`, `custom_all_headings_bottom_margin`. Wrong key (`select_custom_heading_font`) is a silent no-op — h4/h5/h6 fall back to Kajabi's default heading font (often Inter), so `pricing_card` names (h4) and other small headings render in the wrong font while h1–h3 look correct. PREFER all-headings over per-element overrides as the BASELINE: per-element only covers the levels you author; every skipped level falls back to the Kajabi default which usually looks wrong next to the custom primary. Add `override_h<N>_font_styles` overrides ONLY when a specific level needs different sizing/weight than the all-headings baseline. Symptom: "h1/h2/h3 in custom font but pricing card titles still wrong" → check the field id is `select_custom_all_headings_font` (with `_all_`). Verified in `pro-unlocked/snippets/font_override_styles.liquid:78` (selector covers h1–h6 + their `strong`) and `config/settings_schema.json`. See `mem://reference/pro-all-headings-font-field-id.md`.
EXPLICIT FONT WEIGHTS (Pro templates) — Every Pro template's `themeSettings` MUST explicitly set `font_weight_heading` + `line_height_heading` + `font_weight_body` + `line_height_body` (Standard fields), AND for every heading level (h1–h6) actually rendered: `override_h<N>_font_styles:"true"` + `custom_h<N>_font_weight` + `custom_h<N>_line-height` + `custom_h<N>_font_size_desktop` + `custom_h<N>_font_size_mobile`. Same for body (`override_body_fonts:"true"` + weight/lh/sizes) and buttons (`view_advanced_button_customizations:"true"` + `btn_font_weight` + sizes). NEVER rely on Kajabi defaults or `"inherit"` — catalog defaults (e.g. heading=700) often diverge from the loaded font's actual Kajabi default (often 500/600 for serif display fonts), causing preview h1 to render heavier than Kajabi's h1. Pre-flight every template build: walk every page, list every heading level, confirm each has explicit override values. See `mem://reference/template-explicit-font-weights.md` and AGENTS §4.22.
STYLE GUIDE FIRST, BLOCK OVERRIDES SECOND, CUSTOM CSS LAST RESORT (cascade discipline) — Every styling decision (fonts, colors, buttons, spacing, type sizes) cascades in this exact order: (1) `themeSettings` (style guide) sitewide — Pro custom font system (`use_custom_fonts:"true"` + `font_link_*` + `select_custom_all_headings_font:"primary"`) or Standard `font_family_heading`/`color_button`/etc.; (2) per-block overrides ONLY when one block must differ from sitewide (e.g. one CTA in light pair); (3) `customCss` LAST RESORT, only when style guide genuinely can't express it (e.g. `.logo__text` per AGENTS §4.35f, Kajabi-rendered DOM with no schema field). 🚨 NEVER hand-write `@import url(fonts.googleapis...)` + `body{font-family:...}` in `customCss` when `themeSettings` could express it — silently overrides the expert's style-guide UI tweaks and creates "I changed the heading font and nothing happened" support bugs. NEVER hand-write `:root{--pathx-color-*}` / `body{color:...}` / `.btn{background:...}` either — they bypass the style guide editor entirely. Pre-flight every site build AND every styling edit: open `themeSettings` (set fonts/weights/colors/buttons there FIRST), then audit `customCss` and migrate any typography/color rules that duplicate style-guide capability. Only rules that survive in customCss: `.logo__text`/`.pricing__heading` typography, animations, complex selectors, `@media` beyond Pro's mobile sizes. See `mem://reference/style-guide-cascade-discipline.md` and AGENTS §4.35ad.
WHITE-ON-WHITE BLOCKS VANISH — NEVER place a chrome-bearing block (`pricing_card`, `accordion`, `feature`, `card`) with `backgroundColor:"#FFFFFF"` inside a `content` section whose `background` is also white. Verified Kajabi shadows (§4.18) are too gentle to define a boundary — cards render edgeless on the live site even though the preview LOOKS fine (PricingCard.tsx defaults to a hairline border in preview; `serializeChromeProps` doesn't even emit `border` to Kajabi). **THINK LIKE A DESIGNER — tint the BLOCK, not the section.** Default fix: warm ivory `#FBF6EC` (warm palettes) or cool `#F7F8FA` (cool palettes) on the BLOCK's `backgroundColor`. The card becomes a deliberate light-register object that pairs with any dark "highlight" tier in the same grid; every section keeps its rhythm. NEVER tint isolated sections to "make cards visible" — that creates a blotchy, reactive page palette where some sections are cream and others white for no compositional reason (the expert will call it out as an afterthought). Section-tinting is a LAST RESORT, only justified when the section is the only content section on the page OR the page already alternates tinted/white bands by design. Hairline `border` is preview-only (engine doesn't serialize it). Dark highlight tiers unaffected. See `mem://reference/white-on-white-blocks.md` and AGENTS §4.23.

FEATURE BLOCK IMAGE WIDTH (CRITICAL — #1 repeated complaint) — `feature` block's `imageWidth` defaults to **80px** (icon size) when omitted. There is NO auto-fill-the-card mode. UNLESS you want the image SMALLER than the card it lives in (i.e. it's an icon), you MUST set `imageWidth` explicitly to a LARGE pixel value EVERY TIME. Card photos: `"480"`–`"640"` (3-up/4-up grids), `"800"`–`"1200"` (2-up split), `"1400"+` (full-bleed). Icons: omit or `"32"`–`"120"`. FORBIDDEN on photos: omitted, empty, or anything `< 320`. Symptom mapping → check imageWidth FIRST: "images are tiny / postage stamps / icons", "make the images bigger" (especially repeated), "service cards: text huge but photo a dot". Pre-flight EVERY build: walk every `feature` block with `image` set; if photo, confirm `imageWidth >= "320"` (default `"480"`). NO middle ground — either icon (≤120) or photo (≥320, usually 480+). See AGENTS §4.17 and `mem://reference/feature-block-image-width.md`.
SIBLING IMAGES IN A GRID = ONE ASPECT RATIO (CRITICAL — REPEAT COMPLAINT, applies to `image` blocks too not just `feature`) — Whenever you generate 2+ images that will sit side-by-side in the same row (`image` gallery, `feature` 3-up, `pricing_card` row, `card` grid), DECIDE ONE ASPECT RATIO FIRST (4:3 default editorial, 1:1 portraits, 16:9 cinematic) and pass that EXACT `aspect_ratio` to every `imagegen` call. Never let the model pick — the prompt picks the subject, YOU pick the ratio. `equalHeight` does NOT save you (it sizes cards, not images). Belt+suspenders: tag the section with `customCssClass:"uniform-grid"` (+ snake_case sibling) and emit sitewide CSS clamp `.uniform-grid .image,.uniform-grid .image__image,.uniform-grid .image img,.uniform-grid .feature__image img{aspect-ratio:4/3!important;width:100%!important;height:auto!important;object-fit:cover!important;max-width:none!important}` so even mismatched sources clamp to a uniform crop. Symptoms ALL = check this rule FIRST: "images different sizes/heights", "row looks ragged/off", "I told you to make images same ratio" (expert has said this multiple times — do not let it happen again). See AGENTS §4.35ah and `mem://reference/feature-grid-uniform-aspect-ratio.md`.
BLOCK CONTENT PROPS — `update-site-design` accepts arbitrary JSON without validating prop names. Wrong prop names sit valid in JSON, save returns 200 OK, re-fetch shows them present, BUT renderer ignores unknown keys and draws block from defaults. Three save cycles can pass before anyone notices "nothing changed." ALWAYS read the block's component file in the engine BEFORE authoring `props` — find the `*Props` interface; that's the field whitelist. Verified silent-drop renames: `pricing_card` → `title`→`name`, `description`→`text`, `priceSubtext`→`heading`, `featured`→`highlight`, `badge`→`badgeText`, `accentColor`→`brandColor`, inline-styled `<ul>`→plain `<ul><li>` (engine's `decorateFeatureList` auto-wraps); `feature` → `description`→`text`, `imageUrl`→`image`, no separate `title` (write inline `<h3>` in `text`); `cta` → `text`/`title`→`label`, `href`→`url`; `image` → `url`/`imageUrl`→`src`; `accordion` → `title`/`header`→`heading`, `body`→`text`. 200 OK ≠ change took effect; only the render does. Symptom "card looks identical after save" → suspect prop names FIRST (before chrome, padding, renderer, save endpoint). See AGENTS §4.26 and `mem://reference/block-prop-names-engine-source-of-truth.md`.
SITEWIDE CSS RESETS BEFORE COMPOSING (AGENTS §4.30 step 3a) — Four Kajabi defaults silently leak through brand styling and cause "why does this look off" bugs that only surface after the site is half-built. Emit ALL FOUR in `customCss` on every NEW site, BEFORE composing pages: (1) `.btn{box-shadow:none!important}` + header-scoped variant — Kajabi base ships shadow that mismatches flat brand buttons (`mem://reference/button-shadow-reset.md`); (2) `.feature .btn--text{padding:0!important;...}` — base `.btn` 9.5px×30px padding leaks into text-style buttons because Pro's zero-padding override is `#block-{id}` scoped (`mem://reference/feature-text-button-padding-leak.md`); (3) `.footer_pro .link_list__title,...ul,...li{text-align:left!important}` — Pro centers `.link_list__title` by default; restyling font/color without resetting alignment leaves titles centered while lists go left (`mem://reference/footer-pro-link-list-title-centered-default.md`); (4) `.feature .feature__image,.feature__image img{border-radius:0!important}` — EVERY base theme (Streamlined, Streamlined-Pro, Encore, Encore-Pro) auto-rounds feature images into circles by default (`mem://reference/feature-block-square-images-mandatory.md` + AGENTS §4.35ag — also set `imageBorderRadius:"0"` + `image_border_radius:"0"` on every feature block with an image). Partial overrides (set color, ignore alignment/padding/shadow/radius) leave the Kajabi default visible alongside your override — when overriding ANY Pro default, reset EVERY property the default touches.

EDITORIAL HTML CONTENT REQUIRES INLINE STYLE — §4.35ad bans inline `style="..."` for RECURRING styling (h1–h6, body, buttons, links — those belong in `themeSettings`). But ONE-OFF editorial copy where the visual treatment IS the content (testimonials, pull quotes, signature lines, magazine-style hero callouts) REQUIRES inline `style="..."` on the specific `<blockquote>`/`<cite>`/`<p>`. `themeSettings` only covers semantic tags; there's no field for "pull-quote treatment." Pre-flight every site: scan testimonial/proof/quote/signature sections — if copy is raw `<p>...</p>` with no inline style, it'll render as flat body copy on Kajabi. Lift to inline-styled `<blockquote style="font-family:...;font-size:32px;line-height:1.4;...">` matching the brand's editorial voice. See `mem://reference/inline-style-html-content.md` and AGENTS §4.30 step 5.
🚨 PRO SLIDER MINIMUM BLOCKS (≥2 SLIDES REQUIRED) — Whenever `enableSlider:true`, the slide-eligible block count (total blocks − `block_offset` − `block_end_offset`) MUST be ≥ `blocksPerSlide × 2`. A 3-up slider needs ≥6 slide blocks; 2-up needs ≥4; 1-up (testimonial fade) needs ≥2. With only one slide's worth of content the arrows do nothing, autoplay has nowhere to go, loop can't loop — section looks broken/static. If you don't have enough blocks, either (a) ask the expert for more, (b) lower `blocksPerSlide` so the math works, or (c) drop the slider and use a static grid. Pre-flight EVERY slider section: count blocks, subtract offsets, confirm ≥ blocksPerSlide×2. Companion to `mem://reference/pro-slider-block-offset.md` and `mem://reference/slider-fade-stacks-slides.md`. See `mem://reference/pro-slider-minimum-blocks.md`.

🚨 BUTTON CONTRAST vs SECTION (REPEAT OFFENDER — flagged multiple times) — Every button-bearing block (`cta`, `feature`/`pricing_card`/`card` with `showButton:true`, `form` submit) MUST have a button bg/border/text color that visibly contrasts with the section's `background`. Failure shapes: (1) section dark + button dark/unset → vanishes; (2) section white + button white/transparent → same; (3) section cream + button sand (ΔL<8 same hue) → tonal smear; (4) **form blocks** render submit via SITEWIDE `themeSettings.form_input_button_*` / `color_button` — per-block `btn_background_color` often silently ignored; set BOTH per-block AND themeSettings; (5) palette-swap leftovers — section bg missed in a dark→light pass, button still targets new palette. Solid: btn_bg ≠ effective_bg (different hue OR ΔL≥25). Outline: border ≠ bg. Text (§4.16): visible color ≠ bg. Pre-flight EVERY save touching a button OR section bg: walk every section, every button-bearing block, fix any blend before saving. Mnemonic: **a button you can't see isn't a button.** AGENTS §4.35al + `mem://reference/button-contrast-vs-section.md`.

🚨 OVERLAY / SECTION BG CHANGE → RE-AUDIT INLINE `color:` STYLES (companion to BUTTON CONTRAST) — Whenever you change a section's `background`, `bgType`, or overlay (especially dark↔light flip), audit EVERY block's `text`/`html` HTML for inline `style="color:..."` and re-evaluate vs the new bg. Inline editorial colors (per `mem://reference/inline-style-html-content.md`) are the right pattern but they DO NOT auto-adjust — light text on a newly-light bg is invisible (and vice versa). Verified Carrie Variation hero 2026-05-10: dark→light overlay flip left a `<p style="color:rgba(244,239,230,0.85)">` lede invisible. Pre-flight: grep section blocks for `style="[^"]*color:` after any bg change; flip any value that fails contrast. Run alongside §4.35al button-contrast audit on the same pre-flight pass. AGENTS §4.6a + `mem://reference/overlay-change-reaudit-inline-colors.md`.
